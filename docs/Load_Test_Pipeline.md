## Reading this

`POST /v1/ride-requests` measures the **front door only** — validate, assign a request id, publish to the Redis Stream, return 202. It deliberately does not include matching, because matching happens in a later batch window and the rider's client is not waiting on it. That separation is the reason a rider can still submit while the engine is restarting.

End-to-end time to a *match* is bounded by the batch window (ADR-0005), not by this latency: a request arriving just after a flush waits nearly a full window. The batcher reports that separately as `queue_wait_p50`.
