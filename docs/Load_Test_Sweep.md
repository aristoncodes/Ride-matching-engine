## The claim under test

The TDD claims matching is near **O(N log M)** rather than **O(N·M)**, where N is riders and M is candidate drivers:

```
each rider's k nearest drivers  ->  quadtree query, ~O(log M)
solve over N*k edges            ->  grows with N, barely with M
```

Two falsifiable predictions follow:

1. **Doubling N roughly doubles the time.**
2. **Doubling M barely moves it.** If time instead scales with M, the quadtree shortlist is not working.

**Prediction 2 holds emphatically. Prediction 1 does not** — see the verdict below. The measurements are reported as taken rather than trimmed to fit the claim.

Timings are the engine's own `compute_micros`, which excludes serialization and the loopback round trip, so this isolates the algorithm from the transport. Median of 7 runs after an untimed warm-up.

## Verdict

### M (drivers): the claim holds, strongly

**32x the drivers (500 -> 16,000) costs only ~2x the time.** Every doubling of M multiplies the time by 1.02-1.27, against the 2.0 that an O(N·M) design would show. The quadtree shortlist is doing exactly what Week 2 built it for: the driver pool can grow enormously without the matcher noticing.

### N (riders): the claim is WRONG, and the real cost is superlinear

Doubling N multiplies the time by 1.5-4.7, not 2.0. Fitted across the whole range, **32x the riders costs ~100x the time — roughly O(N^1.33)** at these sizes.

This is not a bug, it is the min-cost-max-flow solver being described incorrectly by the original claim. Successive Shortest Paths performs **one augmentation per matched rider**, and each augmentation is a shortest-path search over a graph whose edge count is itself O(N·k). So the solve is closer to **O(N^2 k log N)** in the worst case — quadratic in N, not linear. The `log M` term is real and belongs to the *candidate lookup*, not to the solve.

**A more honest statement of the complexity:**

```
candidate shortlist :  O(N log M)      <- confirmed by sweep B
solve               :  ~O(N^1.3..2)     <- measured by sweep A
dense alternative   :  ~O(N^2.9)        <- measured by sweep C
```

### Why this matters operationally

Because the cost is superlinear in N, **the batch size cap is a latency control, not just a memory bound.** A 3200-rider batch takes ~328 ms; four 800-rider batches take ~158 ms in total for the same riders. Splitting a large batch is strictly faster, at some cost in match quality since each smaller batch optimises over a smaller pool. That trade-off is exactly what `MAX_BATCH` exposes, and this table is the evidence for choosing its value.

The dense control confirms why the sparse path exists at all: doubling both N and M multiplies dense time by ~6-10x, so at N=M=800 it takes **~2 seconds** — already past the 3-second batch window on its own.
